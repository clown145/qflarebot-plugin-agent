# Skills

Skills 是**可复用的能力包**：一段 Markdown 指令，让模型在特定任务下按你写好的流程做事。

## 为什么要有它

把「怎么做事」写进系统提示词，会让每一轮对话都背着全部流程 —— 你的 token 全花在
说明上，而不是回答上。Skills 解决这个：**平时只给模型一个目录，需要时才加载全文。**

这叫**渐进披露（progressive disclosure）**：

| 时机 | 注入什么 | 成本 |
| --- | --- | --- |
| **每一轮** | 只注入目录：`- <id>: <description>`，最多 40 条 | 便宜 |
| **用户激活某个 skill 时** | 注入该 skill 的完整 `SKILL.md` 正文 | 贵，但只在需要时 |

所以你可以挂十几个 skill，日常对话的额外开销仍然只有十几行目录。

## 用法

用户在对话里显式激活：

```text
/skill 写周报 把这周的提交整理成周报
```

- `写周报` 是 skill 的 **id**
- 后面的文字会**替换掉**原本要发给模型的消息（`/skill` 这段不进模型）

激活后，该轮的上下文多一条 `system` 消息，内容是 skill 的完整正文。

> **为什么是显式激活而不是自动匹配**：自动匹配要判断「这条消息属于哪个 skill」，
> 而那个判断本身要么又是一次模型调用（贵），要么是关键词匹配（容易错）。
> 显式 `/skill` 零成本且不会误触发 —— 与 serverless-agent 的选择一致。

## SKILL.md 格式

```markdown
---
name: 写周报
description: 把本周的代码提交和 issue 整理成一份中文周报
---

# 写周报

## 步骤

1. 用 `http.request` 拉取仓库本周的提交
2. 按模块归类，不要逐条罗列
3. 输出格式：本周完成 / 进行中 / 风险

## 注意

- 不要编造没发生的提交
- 日期用 ISO 格式
```

### 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `description` | **是** | **唯一**进目录的字段。写得具体一点，模型靠它判断该不该用 |
| `name` | 否 | 显示名，缺省就用 id |

没有 `description` 的 skill **会被拒绝保存** —— 它在目录里就是一行没有信息量的东西，
模型永远不会激活它，等于没写。

### 约束

| 项 | 限制 | 为什么 |
| --- | --- | --- |
| id | `^[a-zA-Z0-9._-]+$`，1–64 字符 | 要能放进文件路径和命令里 |
| 正文大小 | ≤ 32 KB | 激活时**全文注入上下文**，太大就撑爆了 |
| 目录条数 | 最多 40 条 | 每轮都注入，条数越多每轮越贵（与 serverless-agent 一致） |

## 存储

Skills 存在 **D1 的 `{skills}` 表**（`id` / `name` / `description` / `body` / `updated_at`）。

**为什么不用虚拟工作区（vfs）**：vfs 是给「模型在运行时读写文件」用的，
需要 R2、需要路径校验、每次读要走多层。而 skills 是**运维配置**：
写得极少（只有编辑时写）、每轮都读、体积小。一张表一次查询就能列出全部，
比在 vfs 里遍历目录便宜得多。何况 vfs 默认是关的，skills 不该被它绑死。

**额度影响**：写入只在编辑 skill 时发生，读是每轮一次（D1 读 500 万行/日，
是写的 50 倍）。所以对额度几乎没有影响。

## 与 serverless-agent 的差异

| 项 | serverless-agent | 这里 | 为什么 |
| --- | --- | --- | --- |
| 存储 | VFS 的 `/skills/<id>/SKILL.md` | D1 单表 | 见上 |
| 工具牢笼 | 激活后把 vfs 收窄到 3 个只读工具并限制路径 | **未实现** | 这里的 skill 不拥有文件；如果你需要，可以配合工具栏把写工具关掉 |
| 版本 / 回滚 | 有 revisions | **未实现** | 每次编辑都是额外 D1 写入；个人机器人用不到 |
| 自动编辑 | 模型能写 skill | **不支持** | 让模型改自己的指令是高风险能力，需要二次确认闭环（那还是半成品） |
| 内置 skill | `provision` / `skill-creator` | 无 | 同上 |

## 在哪改

**管理页「技能」区块**：卡片列表 + 「新增技能」按钮。点编辑会打开一个
带 `SKILL.md` 全文的编辑框，可以直接改 frontmatter 和正文。

保存时的校验错误显示在编辑器下方（不是 toast），方便边改边看。

> 编辑时 id 是锁住的 —— 它是主键，改了等于新建一条，很容易误操作。

## 接口

全部 `auth: 'admin'`（只有面板会话或桥接令牌能访问）：

```text
GET    /api/skills        → [ { id, name, description } ]      # 目录，与注入给模型同源
GET    /api/skills/:id    → { skill, content } | 404           # content 是原始 SKILL.md
POST   /api/skills        → { id, content } → { skill }        # 保存（upsert）
DELETE /api/skills/:id    → { ok } | 404
```

`GET /api/skills/:id` 同时返回两种形状：
- `skill` —— 解析后的字段（`metadata.name` / `metadata.description` / `instructions`）
- `content` —— **原始 SKILL.md 全文**（含 frontmatter）

编辑器必须用 `content`。不要用解析后的字段在前端自己拼 frontmatter ——
那等于在两边各实现一遍格式约定，一旦不同步就会「编辑一次就把 frontmatter 改坏」。

保存时的校验错误（id 非法 / 超 32KB / 缺 `description`）会**直接把消息回给页面**，
运维当场知道写漏了什么，而不是等某次对话才发现技能「消失」。

## 权限

`skills.*` 工具的权限级别见 [工具与权限](./tools.md)。
**注意**：激活 skill 会注入任意你写的指令到上下文 —— 写 skill 的人等于能指挥模型。
所以 skill 的**管理入口只有管理页（`auth: 'admin'`）**，普通群成员只能激活，不能创建。

## 排障

| 现象 | 原因 |
| --- | --- |
| 目录里看不到某个 skill | 它没有 `description`（保存时会被拒），或超过 40 条被截断 |
| `/skill xxx 你好` 没反应 | id 不存在，或 id 里有非法字符 |
| 激活了但模型没照做 | 正文写得太含糊。skills 是指令，不是魔法 —— 步骤要具体到「用哪个工具、输出什么格式」 |
| 每轮 token 明显变高 | skill 条数多（目录 40 条），或某个 skill 正文接近 32KB |
