# 排障

## 症状 → 原因

### 机器人不回复

按这个顺序查，**前一步没过就别看下一步**：

| 检查 | 怎么查 |
| --- | --- |
| 1. 消息有没有唤醒？ | 群里必须 **@机器人** 或 **以 `wake_prefix` 开头**。普通群聊消息默认不理 |
| 2. 是不是被当成指令了？ | 以 `command_prefixes`（默认 `/`）开头的消息交给指令，**不进模型** |
| 3. 内容安全拦了？ | 日志搜「入站内容命中安全关键词」 |
| 4. 频率限制拦了？ | 用户会收到「说得有点快」。日志搜「触发频率限制」 |
| 5. LLM 服务可用吗？ | 用户会收到「需要的『LLM 接口』插件没有启用」 |
| 6. 会话在忙？ | 同会话有 run 在跑时，新消息**静默入队**（不回「上一条还在处理」）。等几秒；被执行者被掐断则等 cron 的 10 分钟清理轮 |
| 7. 超预算了？ | 用户会收到「这个问题要多花点时间，我处理完会直接回复你」。任务仍在后台跑 |

### 工具调用被拒

| 错误码 | 含义 | 怎么办 |
| --- | --- | --- |
| `permission_denied` | 级别不够或 scope 缺失 | 看下方「权限」 |
| `needs_confirmation` | 该工具需要二次确认 | **目前无法确认** —— 闭环是断的，见 [工具与权限](./tools.md#二次确认当前是半成品) |
| `unknown_tool` | 模型编了个不存在的工具名 | 正常现象，模型会自我纠正 |
| `tool_not_allowed` | 工具不在本轮白名单 | 检查工具栏有没有关掉它 |
| `skill_tool_not_allowed` | skill 激活时禁用了该工具 | — |

**权限**：单聊 / 群聊的基线不同。单聊是 level 3（能做定时任务和 HTTP），
群里普通成员是 level 2（只能读写工作区），群里角色未知只有 level 1（只读）。
定时任务以 level 3 的身份运行。

### 工作区（vfs）工具完全不见

**`enable_vfs` 默认是关的**，而且要绑 R2。两个条件缺一个，整组 vfs 工具**根本不注册**
（不是调用失败，是模型看不到）。日志搜「enable_vfs 打开了但 R2 未绑定」。

> 为什么整组不注册而不是逐个报错：用户开了开关却只能写小文件会困惑；
> 模型看到一堆必然失败的工具只会反复重试。

### 定时任务不触发

| 检查 | 说明 |
| --- | --- |
| `enable_schedule` 开了吗 | 默认关 |
| cron 在跑吗 | 插件声明了 `tick` = `* * * * *` |
| 任务是给**本会话**建的吗 | `schedule.create` 只能给当前会话建，不能跨群 |
| 延迟合法吗 | 必须 ≥60 秒、≤1 年 |
| 会话当时忙吗 | 到点会先入队；抢不到执行权就等队列 |

### 上下文太长 / 模型开始忘记东西

| 现象 | 原因 | 调法 |
| --- | --- | --- |
| 忘了很久以前的事 | 压缩按轮丢弃，早期轮次被丢 | 这是压缩的**设计行为**。要跨轮记忆就切到 `summary` 模式（多一次模型调用，摘要由 cron 异步生成） |
| token 费用突然变高 | `history_limit` 太大，或 skill 目录条数多 | 调小 `history_limit` / `max_context_tokens` |
| 调大 `history_limit` 没效果 | DO 里历史上限是 **120 条** | 配置上限是 100，所以正常不会撞；但改配置时要和 `MAX_HISTORY_ROWS` 一起看 |

### 发了图片，机器人说读不到 / 当没看见

| 现象 | 原因 | 调法 |
| --- | --- | --- |
| 回复里说「当前模型不支持图片输入」 | 模型的 `capabilities` 里没有 `image` | 去**LLM 插件页面**给那个模型勾上「图片」能力。注意**默认值不含 image**——三种协议的默认能力都只有 text/tools(/json)，不勾就永远走纯文本分支 |
| 说「有一张图片太大」 | 单张超过 **800 KB**（原始字节） | 没得调，只能让用户发小一点的图。这个上限是为了 Worker 的内存与 10 ms CPU 预算，不是随便定的 |
| 说「图片总大小超过上限」 | 一次发的图**合计**超过 1.5 MB | 分几次发。单张都在限内也会撞这条，比如 4 张 600 KB |
| 说「下载失败（HTTP 4xx）」 | QQ 图片链接的签名过期了 | 正常不会发生：图片在**入站时**就下载转码了。如果持续出现，检查 Worker 能否访问 QQ 的图片域名 |
| 完全没反应，也没有任何说明 | 消息里没有正文也没有附件 | 见「机器人不回复」那一节 |

> **为什么入站就下载**：QQ 的图片链接带签名、有效期短，而这一轮对话可能延到
> cron 段才真正跑（最坏 5 分钟后），那时链接近乎必然失效。所以收到消息时就
> 取回来转成 base64，后面不再依赖原链接。

### `/reset` 之后记忆还在

`reset` 做三件事：**打断正在跑的 run → 清空待跑队列 → 删历史**。
如果你在 reset 的同一瞬间又发了消息，那条消息可能已经入队。
历史是删干净了的，看到的是新对话。

### 页面改了设置但不生效

页面覆盖存在 KV 里，`resolveConfig()` 会合并。**如果失效，先确认是哪条路径**：

- **正常消息**：应该是生效的。
- **cron 恢复的滞留 run**：早期这里误用了 `ctx.config`，已修正。
- **定时任务触发**：走的是 cron 路径，用的是 `resolveConfig`，应该生效。

如果确实不生效，看 `/status` —— 它会显示「页面已改；配置里是 …」，
能直接看出两套配置的差异。

## 日志说什么

日志是**结构化 JSON 行**，关键字段：

| 关键词 | 含义 |
| --- | --- |
| `唤醒 Agent` | 判定通过，reason 是 `at` / `prefix` / `private` |
| `消息不唤醒 Agent` | reason 是 `bot-self` / `empty` / `command` / `not-mentioned` / `not-woken` |
| `上下文已压缩` | `droppedRounds` / `tokensBefore` / `tokensAfter` |
| `入站内容命中安全关键词` | `matched` 是命中的词（**只记日志，不回给用户**） |
| `出站内容命中安全关键词` | 模型输出被拦 |
| `触发频率限制` | `retryAfterMs` |
| `内联执行超预算` | 超过 18 秒，转后台 |
| `run 完成` / `run 失败` | `steps` / `toolCalls` / `retryable` |
| `工具权限不足` | `tool` / `reason` / `sources`（sources 能看出命中的是哪条策略） |
| `cron 超出预算` | 剩余会话/任务留到下一轮 |

## 可重试 vs 不可重试

`run` 内部对**可重试错误就地重试一次**（间隔 3 秒），然后才告诉用户：

| 错误 | 可重试 | 用户看到 |
| --- | --- | --- |
| `rate_limit` | ✅ | 「模型服务正在限流，稍后再试一下。」 |
| `timeout` | ✅ | 「模型响应超时了，稍后再试。」 |
| `auth` | ❌ | 「模型服务的 API Key 有问题，请在『LLM 接口』插件页面检查配置。」 |
| `unknown_model` | ❌ | 「配置的模型别名不存在，请检查『模型别名』。」 |
| 超过步数/工具数上限 | ❌ | 「一次对话最多…，已经用完。可以让我少做几步，或者把任务拆开。」 |

**重试只有一次**是有意的：两次都失败说明不是瞬时抖动，继续等只会吃满事件预算。

## 已知限制

| 限制 | 影响 | 现状 |
| --- | --- | --- |
| **Gemini 思考模型的工具调用不可用** | 本地契约副本没有 `thought_signatures`，Gemini 对 functionCall 签名严格校验，缺了 400 | 用非思考模型或 OpenAI 兼容协议没影响 |
| **二次确认闭环是断的** | `sideEffect: 'dangerous'` 的工具永久卡在待确认 | 当前没有这种工具，故为潜在问题 |
| **策略表没有写入方** | 「策略叠加」实际不生效，真实行为是角色基线 | 要叠加只能手工写 `p_agent_policies` |
| **没有 run/step 可观测性** | 没有 `runs` / `run_steps` 表，排障靠日志 | 换来的是每条消息完全不碰 D1 |
| **`summary` 的摘要由 cron 生成** | 压缩后最多等一分钟摘要才生效；这段时间内早期内容只剩 truncate 的效果 | 摘要放在事件路径会吃光 30 秒预算，cron 是唯一安全的位置 |
| **MCP 不支持** | — | stdio 在 Worker 里结构上不可能 |

## 还是不行？

按这个顺序收集信息：

1. **完整日志**（结构化 JSON，按 `conversation` 过滤）
2. **`/status`** 的输出（能看出模型别名、开关、页面覆盖差异）
3. **复现步骤**：哪条消息、在群还是单聊、用户是什么角色
4. **`manifest.json` 与源码是否同步**（`npm test` 里的 `manifest.test.ts` 会告诉你）

排障时**不要只看「工具失败」** —— 很多看起来是工具的问题，
根因是权限级别（单聊 vs 群）或开关（`enable_vfs` / `enable_schedule`）没配。
