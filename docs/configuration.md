# 配置说明

配置有两个来源，**管理页面的改动会覆盖面板配置**：

```text
DEFAULT_SYSTEM_PROMPT  ──> defaultConfig（内置默认值）
                              ↓
                         ctx.config（面板插件配置表单保存的值，权威默认）
                              ↓
                         KV 覆盖层（管理页改的值，只存改过的字段）
                              ↓
                         resolveConfig(ctx)  ← 生产代码一律用这个
```

改回原值时覆盖自动消失，不会留下一条「和默认值一样的覆盖」。

> **已知不一致**：cron 里恢复滞留 run 的那条路径，早期误用了 `ctx.config`，
> 导致页面改的模型对恢复的 run 不生效。已在 `serviceConversationObjects` 里修正为
> `resolveConfig`（懒加载：没有滞留 run 时不额外读 KV）。

## 模型与人格

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `model` | `chat` | 模型别名，来自 LLM 插件。管理页是下拉点选 |
| `system_prompt` | 内置 | 基础系统提示词（人格是**追加**在它后面） |
| `personas` | `[]` | 多套人格 |
| `default_persona` | 空 | 会话没绑定时用哪套；留空则不加人格段落 |

### 图片输入需要显式开启模型能力

用户发图片时，能不能真的交给模型看，取决于**模型声明的能力**：

```
LLM 插件里那个模型的 capabilities 含 image  →  图片转成 image part 发给模型
不含（或没配）                              →  退回纯文本 + 一句「模型不支持图片输入」
```

**默认不含 `image`**：三种协议（openai / anthropic / gemini）的默认能力都只有
text/tools(/json)。所以换了支持视觉的模型（GPT-4o、Claude、Gemini Pro 等）
也要去 LLM 页面**手动勾上「图片」**，否则图片永远走纯文本分支。

图片在**入站时**就下载转成 base64（QQ 的链接签名会过期，而这一轮可能延到 cron 段
才跑）。体积有两道闸：单张 ≤ 800 KB、一次合计 ≤ 1.5 MB，超出的图跳过并在正文里
说明原因，不影响同一条消息里的其他内容。

### 每套人格的字段

| 字段 | 说明 |
| --- | --- |
| `name` | 标识，会话按它绑定 |
| `prompt` | 人格提示词 |
| `begin_dialogs` | 开场对话，每行一句 `user:` / `assistant:`；**必须成对** |
| `tools` | **可用工具白名单**。留空 = 不限；`[]` = 一个都不给 |
| `skills` | **可见技能白名单**。留空 = 不限；`[]` = 一个都看不到 |
| `custom_error_message` | 出错时的自定义回复 |

人格的排列顺序就是配置里的数组顺序（管理页可以上移/下移）。

### 提示词的分层与缓存

system prompt 分三层，**从上到下越来越稳定**：

| 层 | 内容 | 跨轮变化？ |
| --- | --- | --- |
| 基础 + 人格 + 工具规范 | `system_prompt`、人格 `prompt`、工具使用规范 | 不变 |
| 其他插件注入的片段 | `ctx.service('agent').registerPrompt(...)` | 只有插件主动改才变 |
| **本轮动态信息** | 时间、会话类型、说话人 | **每轮变，所以不在 system 里** |

最后一行是关键：模型的 prompt 缓存是**前缀匹配**的，system 里只要有一处每轮变化，
**它之后的全部内容每轮都要重新计费**。

所以时间、会话、说话人被放进 `<system_reminder>`，附在**本轮 user 消息**上，
system 保持 100% 稳定。实测：跨时间、跨用户、跨会话时 system 完全相同。

### 人格提示词是「追加」，不是「替换」

系统提示词分三层，顺序固定：

```text
1. 基础提示词（system_prompt 或内置默认）   ← 身份与语气
2. # Persona Instructions + persona.prompt  ← 人格，追加
3. ## 当前环境（时间/会话/工具规范/回复格式） ← 运行时，每轮都在
```

**为什么不能替换**：第 3 层里的东西是**功能性的** —— 当前时间、当前会话、
工具使用规范、「纯文本不要 Markdown」。替换掉模型就会开始输出 Markdown、
不知道现在几点、也不知道自己有工具。

> 早期实现用的是 `persona.prompt ?? config.system_prompt`（替换），
> 配了人格就丢掉了全部运行时信息。现在有测试专门锁住这一点
> （`wiring.test.ts` 的「人格提示词是追加不是替换」）。

人格排中间、运行时信息排最后：越靠后模型越容易遵守，
而「不要用 Markdown」这类硬约束最需要被遵守。

### 开场对话必须成对

`begin_dialogs` 的约定：**一个 `user` 接一个 `assistant`**。

- 奇数条 → 丢掉最后落单的那条
- 以 `assistant` 开头 → 丢掉开头，直到遇到 `user`
- 只有一条 → 整段为空

为什么必须成对：开场对话是**插在历史最前面**的，落单的 `user`（没有对应的
`assistant` 回复）会让模型以为「上一条话还没回」，从而答非所问，甚至把开场白
当成用户真实的提问。以 `assistant` 开头则更怪 —— 模型一上来就自己说话。

> 配置写歪时只做**最小修正**、不抛错：人格开场白是锦上添花，
> 写坏了不该让整轮对话失败。

### 工具白名单

同一台机器人上，「客服人格」不该能发 HTTP 请求，而「运维人格」需要。
以前只能全局开关工具，没法按人格区分。

`tools` 的语义：

| 值 | 含义 |
| --- | --- |
| 不写 / `undefined` | **不限**，用全局工具集 |
| 数组 | 白名单，只有名单里的能用 |
| `[]` | **一个都不给** |

> `undefined` 和 `[]` **含义相反**，不能糊成一样。代码里用 `!== undefined` 判断，
> 不是 `?? []`。

白名单与全局工具开关**叠加**：先按人格收窄，再减掉全局关掉的。
两者都是「减少」，不会互相抵消。也**不替代权限层** —— 白名单只是收窄，
具体某个工具能不能真跑仍由权限级别 + scope 决定（两道关卡）。

### 技能可见性

`skills` 与 `tools` 语义完全同构：

| 值 | 含义 |
| --- | --- |
| 不写 / `undefined` | 不限，全部技能可见 |
| 数组 | 白名单 |
| `[]` | **一个都看不到** |

**为什么要按人格限制技能**：技能目录每轮都进上下文。一台机器人挂十几套技能时，
「客服人格」不该看到「运维手册」——既省 token，也避免模型激活错技能。

> **只过滤目录是不够的**：用户仍可能手动 `/skill <id>` 激活被挡掉的技能。
> 所以激活路径**也要判**，否则白名单只是「不显示」而不是「不能用」——
> 那是个假的权限边界。

### 自定义错误文案

模型调用失败、超步数上限等情况下，默认回一句通用文案。人格可以覆盖它：

```json
"custom_error_message": "哼，才不是出错了，是你不该这么问"
```

一个毒舌角色突然冒出「处理失败：HTTP 500」会很出戏。留空则用通用文案。

> 只在**错误路径**上解析人格 —— 成功对话不多承担一次 D1 读。

**优先级：会话绑定 > `default_persona` > `system_prompt`。**
绑定的那套被删掉时自动回落，不会让会话突然失去人格。

`begin_dialogs`：每轮插在**历史最前面**，用来锚定说话风格，
不属于会话记忆。每行一句，`user:` / `assistant:` 开头。

## 唤醒

群里**只有两种情况**会让机器人开口：

1. **@ 了机器人**
2. **以唤醒前缀开头**（前缀会被剥掉再交给模型）

其余消息一律不理。这是刻意的：群里正常聊天不该被插嘴。

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `wake_prefix` | `/` | 以此开头的消息唤醒 Agent，并剥掉前缀 |
| `friend_needs_wake_prefix` | 关 | 关：单聊任何消息都触发；开：单聊也要带前缀 |
| `command_prefixes` | `/` | 以此开头的消息交给**指令**，不进模型 |

**`wake_prefix` 和 `command_prefixes` 是两件不同的事**，默认值恰好都是 `/`。
这个巧合曾经导致「任何以 `/` 开头的消息都唤醒 Agent」的 bug（上一版把两者拼进了
同一个列表），现在有专门的回归测试守着。

**没命中任何指令、但被唤醒的消息 → 走 Agent。** 用户 @ 机器人说「你好」，
不该要求他打 `/ask 你好`。

### 刻意不做的

| 不做什么 | 为什么 |
| --- | --- |
| **引用消息就唤醒** | 语义上应该只在「引用了**机器人自己**的消息」时才唤醒，但 QQ 官方推送里拿不到被引用消息的发送者。退化成「有引用就唤醒」会导致群友互相引用聊天时机器人插嘴 |
| **群里所有消息都回复** | 这类模式在群聊里基本都是噪音源。而且它依赖群主开「接收全部消息」，一次事件又只有 30 秒预算，不适合用来做高频主动发言 |
| **`wake_mode` 枚举** | 三个开关（`wake_prefix` / `friend_needs_wake_prefix` / `command_prefixes`）已经够表达。多一层枚举只会让「@/前缀/引用」的组合含义不清 |

## 限额与上下文压缩

| 键 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| `max_model_steps` | 8 | 1–30 | 一次 run 最多几步模型调用。失控的 loop 会烧光时长与 token |
| `max_tool_calls` | 12 | 1–50 | 一次 run 最多几次工具调用 |
| `history_limit` | 20 | 0–100 | 每次带多少条历史给模型 |
| `request_timeout_ms` | 20000 | 1000–25000 | 单次模型调用超时 |
| `timezone` | `Asia/Shanghai` | — | 给 `time.now` 和提示词里的当前时间 |
| `context_compression` | `truncate` | — | `off` / `truncate` / `summary` |
| `max_context_tokens` | 12000 | 1000–200000 | 估算超过就压缩 |

### 上下文压缩

长会话的上下文会一直变长。这里**按「轮」压缩**：

> **一轮 = 一个用户消息 + 紧随其后的所有 assistant/tool 消息。**

压缩只丢**整轮**，所以 **`tool_call` 和它的 `tool_result` 永远不会分家** ——
配对是结构上保证的，不靠事后修补。丢完再跑一次 `fixMessages` 兜底
（它还会丢掉孤儿 tool 消息、保证 system 之后第一条是 user，这是智谱/Gemini 的硬要求）。

**行为细节**：

- **永远保留最新一轮** —— 用户刚说的话不能丢。
- **一次最多丢一半的轮** —— 避免上下文突然断崖式变化。
- **在每一模型步之前检查**，不是每 run 一次 —— 一轮 run 里工具可以来回收很多次，
  结果不断堆进 messages，只在开头压一次等于没压。

**零额度消耗**：`truncate` 是纯内存计算 —— 零模型调用、零 D1 写入、零 KV 写入。
token 按字符估算（CJK 约 0.6/字、其他约 0.3/字符），
不装 tokenizer（那会让包体积涨几百 KB，还要花 CPU，而免费版是全机器人共享 10ms）。
真实用量由模型返回的 `usage` 覆盖估算值。

### `summary` 模式：丢轮 + 异步摘要

`truncate` 的代价是**丢掉的内容真的没了**。会话很长时，用户会说「我刚才不是说过吗」。
`summary` 模式保留这一层记忆：

1. 压缩发生时，被丢掉的那些轮**照常从上下文里移除**（所以省 token 的效果不变）；
2. 与此同时，它们被登记进该会话的 Durable Object（`summary:pending`）；
3. **cron 每分钟那一轮**里，若有待摘要内容，调一次模型生成摘要并存回 DO；
4. 下一轮对话装配上下文时，把摘要插在历史**之前**：
   `system → 人格开场白 → 摘要 → 真实历史 → 本轮消息`。

**为什么不在对话路径里同步摘要**：事件处理器有 30 秒硬窗，一次摘要就是一整次模型调用，
插在回复路径上很可能把预算吃光、用户什么都收不到。cron 没有这个窗口，
而且它本来就在跑（清理与滞留 run 恢复），顺带做一次摘要不会多唤醒 DO。

**成本**：每压一次多一次模型调用。群里闲聊通常几轮就结束，触发不了；
真正连续聊很久的会话才会用到，而那正是它有价值的时候。

**失败怎么办**：模型不可用、调用失败、返回空内容 —— 待摘要内容原样放回队列，
下一轮 cron 继续试，**不会丢**。期间对话照常用 truncate 保底，
用户只会在摘要没生成之前觉得「记性差一点」，不会看到报错。

**什么时候不该用**：如果机器人主要做短问答（每次都是独立问题），
`truncate` 就够了，摘要那一次模型调用是纯浪费。

> **硬上限联动**：DO 里历史最多留 120 条（`MAX_HISTORY_ROWS`），
> 它**必须 ≥ `history_limit` 的上限（100）**，否则用户把配置调大就是静默失效。
> 改这两个值时要一起改。

## 防滥用

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `rate_limit_per_minute` | 10 | 每会话每分钟最多几次对话，0 = 不限 |
| `content_filter_keywords` | 空 | 命中即拒绝（逗号分隔，中英文逗号都行），空 = 关闭 |

### 频率限制

- 计数器放 **Durable Object**，不放 KV/D1。这是**每条消息都读写一次**的热路径；
  免费版 KV 写只有 1,000 次/日、D1 写 10 万行/日（全机器人共享），放上去直接打满。
  而每条消息本来就要唤醒一次 DO，计数等于**零额外成本**。
- 固定窗口（按墙钟整分钟对齐），只存 `{ windowStart, count }` 一个 key。
  滑动窗口要存时间戳数组，读写随次数增长。
- **被限时回一句「说得有点快，等 N 秒再继续吧」，然后放弃。**
  不做「排队等一会儿再回答」那类策略 —— 在 Worker 里 `await sleep()` 会吃光
  30 秒预算然后用户什么都收不到，比直接拒绝更糟。

### 内容安全

只做**纯文本关键词匹配**，两个插入点：

- **入站**：命中的消息不花 LLM 调用、不进队列。
- **出站**：只查入站不够 —— 模型可能把用户诱导出的敏感内容再复述一遍，
  那才是真正发到群里的东西。

提示文案**不暴露命中的关键词**（暴露等于把规则交给用户去试探）。

**为什么不做真审核**：那要调外部 API，而免费版每次调用只有 50 个子请求、
一次事件 30 秒预算，为审核花一个子请求在群聊高频场景下不划算。

## 能力开关

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `enable_tools` | 开 | 工具调用总开关。关掉就是纯聊天 |
| `enable_vfs` | **开** | 虚拟工作区。不绑 R2 也能存 8KB 以内的文本；绑了 R2 才支持大文件 |
| `enable_schedule` | **关** | 动态定时任务（模型能自己建提醒）。需要 cron |
| `enable_audit` | **关** | 把工具调用记进 D1。排障用，**会消耗 D1 写入额度** |
| `show_typing` | 开 | 回复前显示「正在输入」（仅单聊有效） |
| `isolate_sessions` | **关** | 群聊按成员隔离会话（每人一段独立历史） |
| `reply_mention` | **关** | 回复时 @ 说话人（`off` / `group` / `always`） |
| `expose_sender_id` | 关 | 提示词里带上说话人的 openid |
| `expose_datetime` | 关 | 提示词里带上当前时间 |
| `search_api_key` | 空 | Tavily 搜索 Key。留空时 `search.web` 仍注册但返回可读错误 |

### 会话隔离（`isolate_sessions`）

| | 关闭（默认） | 打开 |
| --- | --- | --- |
| 群聊 | 一群人共享一段历史 | 每人一段独立历史 |
| 单聊 | 一人一段 | 一人一段（不受影响） |
| 频道 | 共享 | 每人一段 |

**适合**：客服、多租户、需要「每人一档」的场景。
**不适合**：闲聊群——机器人会失去「刚才大家在聊什么」的共识。

> ⚠️ **切换后已有记忆查不到，等于所有人重新开始。**
> 会话键变了，DO 里那批历史就找不回来了。不做迁移是因为旧历史里
> 压根没存 userId，技术上分不出哪句话是谁说的。

连带影响：人格绑定（`/persona`）和定时任务（`/schedule`）
也都挂在会话键上，隔离后**变成每人自己的**。

### 回复时 @ 说话人（`reply_mention`）

| 值 | 行为 |
| --- | --- |
| `off`（默认） | 不 @ |
| `group` | 群聊/频道 @ 说话人，单聊不 @ |
| `always` | 总是 @ |

**为什么默认关**：群里每条回复都 @ 人会很吵，客户端还会额外推送通知。

**什么时候值得开**：多人同时提问的群。@ 一下，用户一眼能看出机器人在回谁。
「仅群聊」是最实用的中间档 —— 单聊里 @ 对方毫无意义（就两个人），
而且单聊发 `<@openid>` 可能显示成一段裸露的文本。

**实现**：QQ 官方接口没有独立的「@某人」字段，就是在正文里写 `<@openid>`。
用宿主的 `qqAt()` 生成（@ 的格式是平台细节，变了只需宿主改一处），
拼在正文最前面。媒体消息不带 @（会变成独立一行，看着很怪）。

### 让模型知道身份与时间

两个独立的开关，都**默认关**：

| 配置项 | 作用 | 关掉的代价 |
| --- | --- | --- |
| `expose_sender_id` | 提示词里带 `openid: xxx` | 模型分不清群里谁说哪句，没法「记住某个人」 |
| `expose_datetime` | 提示词里带当前时间 | 模型得自己调 `time.now`，**经常忘记、直接凭记忆编日期** |

**关于 openid**：QQ 官方机器人接口只提供 openid（按机器人隔离的匿名标识），
**拿不到真实 QQ 号**。openid 在同一台机器人下对同一用户稳定，换机器人就不同，
不能拿去跨机器人识别。

两个开关控制的都是**本轮 user 消息**里的 `<system_reminder>`，
system prompt 仍跨轮稳定，**不影响缓存**。

### 关于 `enable_vfs` 的 R2 探测

虚拟工作区**分两档**：

| 档位 | 需要 R2 | 能做什么 |
| --- | --- | --- |
| 轻量（默认可用） | ❌ | 读写 8KB 以内的文本、列目录、搜索、移动 |
| 完整 | ✅ | 上面全部 + 大于 8KB 的文件 |

宿主在**未绑定 R2** 时返回的仍然是一个对象（每个方法都是「调用即抛」的桩），
所以 `if (ctx.r2)` 恒为真。插件真的 `r2.head('__probe__')` 探一次，探不到就走轻量档。

> 以前是「没 R2 就整组 vfs 工具不注册」，等于把「记个笔记」这种最常见的用途
> 绑死在重型基础设施上——多数部署里「有虚拟工作区」这句话等于不存在。


### 关于 `search_api_key`

未配置时 **工具仍然注册**，返回「还没配置搜索」的可读错误。
这比整组不注册更诚实 —— 不注册等于假装这个能力不存在，模型会凭空瞎编。
